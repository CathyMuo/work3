## 0. 反馈 #9 之后：立刻切到 p0-r12（**正在跑的 r11 会在解题者训练结束后卡住**）

### 真正的 bug：阶段跑完后卡住不往下走

上游每个脚本都用 `&` 把检索服务（出题者还有奖励 SGLang 服务）放到后台，跑完也不停掉它们。r1–r11 的 `run_p0.sh` 用 `命令 | tee 日志` 记录输出，后台服务继承了这根管道。所以脚本本身结束后，`tee` 还在等这些服务退出，阶段就一直不返回，流程卡在原地。

`timings.txt` 把整个过程记录得很清楚：

| 时间 | 实际发生的事 |
|---|---|
| 11-10 19:54 | 出题者 50 步跑完、检查点写完。训练进程的**退出码是 0**（timings 第二行是 `66706 0`）。日志里那条 DataLoader 报错是 Ray 收尾时打印的，不影响结果。**流程从这里开始卡住**，那个 48–53 GB 的“残留 sglang”就是还没停掉的奖励服务 |
| 11-11 09:31:54 | 厂内运行 `cleanup`，杀掉后台服务，卡住的旧流程才往下走，记下“66706 秒、退出码 0” |
| 09:31:54 → 09:32:01 | 旧流程立即开始题池生成，7 秒后被**同一次 cleanup** 的第二轮 SIGKILL 杀掉（cleanup 先发 SIGTERM，等 10 秒再发 SIGKILL）。这就是 `7 137` |
| 09:32:27 → 14:18 | r10 重新开始题池生成，4 小时 32 分生成完，14:18 写出 parquet |
| 14:18 → 15:28 | 又卡住 70 分钟，原因同上：检索服务还占着管道 |
| 15:28 前后 | 为切到 r11 运行 `cleanup`：检索服务收到 SIGTERM 后正常关闭（日志末尾的 `Shutting down`）。旧流程往下走，题池检查通过，开始解题者训练，4 秒后被同一次 cleanup 的 SIGKILL 杀掉。这就是 `4 137` |
| 15:29:04 | r11 的 `all` 开始，跳过已完成的阶段：15:29:13 的题池检查是它的**第一次**，不是重试。之后正常开始解题者训练 |

所以，反馈 #7 的“退出码 1”、反馈 #8 的“收尾被杀”、反馈 #9 的“解题者 4 秒速死”，都是同一个 bug 的不同表现：阶段跑完后卡住，然后被 cleanup 连带杀掉。r10/r11 的产物检查仍然有用（收尾报错时不会误停），但它们没碰到根因。

### p0-r12 的修复

1. **不再用管道**：阶段输出直接写进日志文件，屏幕上用 `tail -f` 跟随显示。脚本一结束，阶段就返回，然后清理它留下的后台服务。新加的测试专门验证这一点：留一个后台进程，阶段也立即返回；旧代码会一直等那个后台进程结束。
2. **`bash $P0 cleanup` 先停掉同一个 `DRZERO_DIR` 下正在跑的 run_p0.sh**（包括 `all`），再杀它们启动的进程。这样不会再出现“清理把卡住的旧流程放出来，又杀掉它刚启动的下一阶段”。
3. **同一个输出目录同时只能跑一个 run_p0.sh**（flock）。第二个会直接报 “another run_p0.sh is already running” 并退出（退出码 4）。
4. **看板**：r11 之前的耗时记录里混进了卡住的时间（出题者 66,706 秒、题池 21,366 秒）。看板对明显偏大的记录，改用日志里的证据估算：训练按 50 步 × 平均每步耗时，其他阶段按完成的进度条耗时，各加 10 分钟启动时间。这样第 2、3 轮的预计时间不会被拉长。

### 现在怎么做

正在跑的 r11 `all` 里的解题者训练，结束后同样会卡住，整晚都不会往下走。**建议现在就切换**。解题者每 10 步存一次检查点，切换后从最近的检查点续跑，最多损失约 10 步（约 1 小时）。


- 预期的日志：
  - 先跳过出题者和题池；
  - 题池检查约 5 秒；
  - 解题者训练从最近的检查点续跑。如果还没存过检查点，就从头开始。
- 之后全程无人值守：iter1 的转 HF → eval1 → iter2 → eval2 → iter3 → eval3 → eval0 → gate。
- 不需要重新 `patch`。
- 看板要重启一次。
- **以后不要在流程运行时单独执行 `cleanup`**，除非就是想停掉它：r12 的 cleanup 会先停掉整个流程。

## 1. 开跑前：停掉显卡保活程序

## 4. 变量

```bash
conda activate drzero
export DRZERO_DIR=<工作目录>/drzero
export MODEL_3B=<models>/Qwen2.5-3B-Instruct
export CORPUS_JSONL=<models>/wiki-18/wiki-18.jsonl
export INDEX_PATH=<models>/wiki-18/e5_Flat.index
export E5_MODEL=<models>/e5-base-v2
export TRAIN_PARQUET=<models>/nq_hotpotqa_train/train.parquet
export TEST_PARQUET=<models>/nq_hotpotqa_train/test.parquet
export NGPU=4
P0=<工作目录>/work3/scripts/p0/run_p0.sh
```

可选变量：
- `RET_PORT` / `REWARD_PORT`：检索服务和奖励服务的端口，默认 8100 / 8101。
- `CHAL_ROLLOUT_MEM`：出题者训练内 SGLang 的显存比例，默认 **0.25**（与上游相同；**不要调高**，见第 6 节）。
- `SAVE_FREQ` / `CKPT_KEEP`：每多少步存一次检查点、每个运行保留几个，默认 10 / 2（上游是 25 步存一次、全部保留）。
- `FORCE=1`：重跑某一轮时，连已完成的子步骤也重新跑。
- `TRAIN_MICRO`：训练和计算对数概率时每张卡每次处理几条样本（微批次），默认 **1**（上游 2）。总批次 256 和每步的优化更新不变，只是拆得更细，见第 6 节。
- `EXPANDABLE_SEGMENTS=1`：给所有阶段设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，用来缓解显存碎片。**默认关闭**，只作为第二道保险，开启后要确认训练能正常启动。
- `EVAL_ROLLOUT_MEM`：评测时的显存比例，默认 0.6。
- `ROLLOUT_TP`：出题者、解题者、评测在训练内采样的张量并行，默认 **1**（上游 2）。
- `REWARD_TP` / `REWARD_DP`：出题奖励服务的并行方式，默认 tp=2、dp=2（与上游相同）；`REWARD_METRICS=1`（默认）为它打开运行指标。
- **不要调** `train_batch_size`、`ppo_micro_batch_size_per_gpu`：见第 6 节。
- `GEN_MEM`、`FAISS_GPU=0`：显存不够时用，见第 6 节。

**看板**（推荐一直开着）：

**更新看板版本后必须重启看板服务**（Ctrl-C 后重新运行上面的命令）：页面文件每次刷新都会重新读取，但后端是启动时加载的，不重启就看不到新字段。不过新版页面在后端是旧版本时也会自己算出“本步骤预计还需多久”。

看板是只读服务：所有内容都从运行目录和仓库文件读取，不写任何东西，每 8 秒刷新一次。页面分四块：

- **实验进度**：
  - 顶部是研究路线：P0 → P1 → P2 → 主实验 → 投稿。每一站显示状态、**还需 / 预计需要多少时间**、冻结门槛和关键结果；标题旁是 P0–P2 合计还需多久。还没开始的 P2 两臂，按 P0 实测的各阶段耗时估算。
  - 每个运行有一个总进度条，旁边写着整个阶段（如 P0）还需多久、预计几点完成。
  - “正在进行”框写明**本阶段还需多久、预计几点完成**（按最近 5 步的平均耗时估计），并用一句话说明这一步在做什么，再给出训练第几步和本步内的采样进度。
  - 三轮训练各占一条泳道，每条只分 4 段：出题者训练、生成题池、解题者训练、评测。段宽按耗时比例，每段下面标注“用时 / 剩余 / 约多久”，评测段上直接显示 EM；泳道右侧是**本轮合计、已完成、剩余**。末尾是“收尾”（基座评测、门槛判定）。
  - 评测完成后，各轮 EM 会和论文值、0.306 门槛并排显示。
  - 原始子步骤、检索服务、告警和日志都收在“详情”里。
  - 页面底部是每张卡的利用率、功率和显存条。
- **训练曲线**：
  - 可以选任意运行、任意训练或评测阶段。verl 每一步打印的全部数值指标（`critic/`、`actor/`、`response_length/`、`num_turns/`、`timing_s/`、`perf/`、训练中的验证 EM `val-core/…` 等）按组列出，点选即可画图；所选指标会记住。
  - 提供“常用指标 / 验证 EM / 耗时·吞吐”三个一键组合。
  - 可以叠加三轮对比，横轴换成本轮内步数；也可以做平滑。
  - 鼠标悬停显示每一步的数值；出题者奖励单独成图。
  - P2 各臂另有出题奖励日志的曲线：平均难度分、信号占比 w、噪声占比 η、k 分布、每步生成 token 和耗时。
  - GPU 功率、利用率、显存，以及检索延迟和请求数的历史曲线：看板启动后每 10 秒采样一次，只存在内存里，保留 6 小时。
- **研究说明**：一份可以直接给导师讲的图文页（`research/briefing.html`），依次讲背景、问题、核心思路、NCP 方法（带两张示意图和三类题的对比表）、和已有工作的区别、实验设计与门槛、预期贡献、风险和时间线。

### 时间花在哪里（厂内反馈 #3 实测）

出题者每步约 452 秒，其中约 429 秒（94%）是**出题奖励采样**：独立的奖励 SGLang 服务让解题者把每道题答 5 次，每次都是多轮“思考→搜索→作答”。真正的反向传播只有约 23 秒。由此可得：

- **不要调 batch size**：`train_batch_size`、`ppo_micro_batch_size_per_gpu` 只影响那 23 秒，翻倍也只能省约 2%；而且训练峰值时卡 0 只剩 0.5 GB，一调就会显存不足。
- **训练内采样的显存比例**（`CHAL_ROLLOUT_MEM`）调大没有用，反而有害：它管的是出题者自己出题用的那个引擎，不是奖励服务，所以厂内实测没有提速。而且这个引擎每一步都要重新占用这部分显存（verl 先唤醒它，再把训练好的权重同步过去）。卡 0 上本来就多放了检索编码器和奖励服务，出题者的回答越来越长，训练侧的峰值也在上涨，所以 0.45 在第 16 步撞线 OOM。p0-r6 已退回上游的 0.25，卡 0 因此多出约 16 GB 余量。
- 每步要打分的题数会随训练增加：格式合格的题越来越多，最多 256 题 × 5 次 = 1280 次解答。所以后期每一步会比前期慢，看板的剩余时间已改为按最近 5 步的平均耗时估计。

### p0-r5 做了什么

| 改动 | 作用于 | 预期 |
| --- | --- | --- |
| 训练内采样 `tp=2 → 1`（`ROLLOUT_TP`） | 出题者出题、**解题者训练的全部采样**、评测 | 2 个引擎变成 4 个，每张卡各跑一个完整的 3B 模型。解题者阶段同样以采样为主，预计提速最明显 |
| 奖励服务开启 `--enable-metrics` | 出题奖励采样 | 只增加观测：运行中 / 排队请求、KV 缓存占用、生成吞吐，看板“训练曲线”页会画出来 |
| `bash $P0 probe` 速度诊断 | 任意时刻 | 只读，约 2 分钟：每张卡的利用率、每张卡上是什么进程、奖励服务的并行方式和 KV 容量、排队情况、检索延迟，并给出一句话结论 |

奖励服务的并行方式**先不改**（仍是 tp=2、dp=2），因为要对症下药：

- 按 SGLang 0.4.6.post5 的源码，`dp=2, tp=2` 应该是 DP0 用卡 0–1、DP1 用卡 2–3，请求轮流分配，4 张卡都会参与。反馈里卡 2、3 全程 0%，与设计不符。请先跑一次 `probe`，它会列出每张卡上有哪些进程。
- **如果 probe 显示卡 2、3 上没有奖励服务进程，或者有进程却从不计算**：说明 DP 没有生效。从下一个出题者阶段起设 `REWARD_TP=1 REWARD_DP=4`，重跑 `patch`，让 4 张卡各跑一份完整的解题者。
- **如果 probe 显示“KV 缓存经常占满且有请求排队”**：说明是显存瓶颈。但训练峰值时卡 0 已满，奖励服务的显存比例没法再提，请把 probe 的输出发回，家服再想办法。
- **如果 probe 显示“同时只在处理很少的请求、也没有排队”**：说明是长尾。少数题要做满 5 轮，而且每轮最长可生成 2560 token，只能等它们跑完，这部分时间不改协议就省不掉。

### 反馈 #5 之后的结论（2026-11-10）

- **`tp=1` 提速 39% 并保留**：每步从 452 秒降到 274 秒，四张卡显存均为 31–32 GB。
- **奖励服务保持 `tp=2, dp=2`，不改**：
  - probe 显示四张卡的忙碌比例相近（26–30%），说明 DP 是生效的；
  - 奖励服务平均只有 9.7 个请求在跑、零排队、KV 只用 5%，说明它是延迟受限，而不是吞吐受限；
  - 延迟受限时，`tp=2` 的单条生成比 `tp=1` 更快，所以不改。
- **剩下的空转是同步强化学习固有的长尾**：每一步都要等这批题全部打完分才能更新。最后剩下的少数轨迹要串行做最多 5 轮“生成（每轮最多 2560 token）→检索”，单条就要一两分钟，其余 GPU 只能等。这段时间不改 Dr. Zero 的算法就省不掉；在 P0 复现中，算法不能改。
- **不采用“按跳数分批”（方案 A）**：
  - SGLang 是连续批处理：短题做完立刻退出，不存在“短题陪着长题等”；
  - 现在并发远未饱和（零排队），所有题一到就同时在跑，一步的耗时 ≈ 最慢那条轨迹的耗时；
  - 分成 4 批依次跑，总耗时会变成“第 1 批最慢 + 第 2 批最慢 + …”，只会更长；
  - “长的和长的放一起”只在并发打满、需要排队时才有用，现在不是这种情况。
- **不采用方案 B（先探测、再分批）**：和方案 A 的理由相同，而且探测本身还要花时间。
- **不提高 `max_parallel_calls`（方案 C）**：它只管一个回合里并行几次工具调用；并发也不是瓶颈（零排队）。
- **HRPO 的跳数分组只作用在“计算优势”这一层**，不参与采样调度。这是 Dr. Zero 的设计，不是 bug；把它扩展到调度层也无益，理由同方案 A。
- **检索不是瓶颈**：
  - 厂内实测单次检索约 25 ms，判断正确；
  - p0-r7 起，统计里区分了两种延迟：“含高峰排队”的端到端延迟，和“低负载时”（请求到达时前面最多 2 个）的处理时间；
  - probe 只按后者判断检索快慢。

### 各阶段的正常表现（用于判断，不是硬性指标）

| 阶段 | 功率 / 利用率 | 说明 |
| --- | --- | --- |
| 反向传播 | 450–620 W，>90% | 已接近满载 |
| 出题奖励采样前段（并发多） | 4 张卡都应有明显利用率 | 某张卡长期为 0，就跑 `probe` |
| 出题奖励采样尾段 | 100–150 W，接近 0% | 少数轨迹在多轮“生成→检索”之间等待，属于延迟瓶颈 |

### 关于反馈 #2、#3 里的问题

- **HRPO 的跳数分组是生效的**：`grpo_batch` 用 `data_source`（即 `search_zero_{跳数}`）分组，对奖励做组内标准化。但它作用在“计算优势”这一步，不负责调度采样，所以在采样日志里看不到按跳数分批，也不会缩短采样时间。
- `max_parallel_calls=64`：指一个回合里最多并行几次工具调用，跟请求并发数无关，调大没有用。检索线程池有 120 个线程，也不是瓶颈；检索延迟可以在看板上直接看。
- **`Error on 1/5 attempt: ConnectTimeout`**（反馈 #4）：这是奖励采样客户端连接奖励服务（8101）时，TCP 连接没能及时建立。原因是同时发起上千个请求，奖励服务一时接不过来。上游客户端会自动重试（等 1、2、4、8 秒），重试后都成功了，只耗几秒，和这次 OOM 无关。只有一步里出现几十次以上，或者出现 `Failed after 5 attempts`，才需要反馈。
- **每步的采样量越来越大**（595 → 840）：这一点判断正确，后期每步会更慢。但这不是 KV 缓存在膨胀：SGLang 的 KV 缓存在启动时就按比例一次性占好，不会随请求增长。真正上涨的是训练侧峰值，因为出题者的回答越来越长，计算对数概率时的激活也越大。这正是要给训练侧留足余量、不能把 SGLang 的显存比例调高的原因。
- `undefined function: query / answer`：出题者偶尔写错工具名，属于模型采样错误，提示词与工具描述是匹配的。这类 rollout 基本拿不到格式分，出题者会从奖励里学会避免。P0 不能改提示词。

### 显存：两次 OOM 的原因与处理（反馈 #4、#6）

| | 第 16 步（r2） | 第 30 步（r7） |
| --- | --- | --- |
| 位置 | 唤醒出题者引擎、同步权重 | 训练侧反向传播 |
| 原因 | 出题者 SGLang 显存比例 0.45，每步都要重新占回约 36 GB | 出题者回答越来越长，每次前向 / 反向要处理的 token 越来越多，激活和 logits 随之变大（42→59 GB） |
| 处理 | r6 退回上游 0.25 | **r8 把微批次从 2 降到 1** |

**为什么是微批次**：
- 每张卡每步要处理 64 条样本（256 ÷ 4）。上游每次前向 / 反向放 2 条，r8 改成 1 条，分 64 次累积梯度。
- 累积后的总批次和每步的优化更新都不变，但单次处理的 token 数减半，所以随回答变长而增长的那部分显存峰值也减半。
- 训练只占每步约 5% 的时间，所以每步只多十几秒。
- 这对第 2、3 轮同样有效：回答长度有上限（出题者最多约 3200 token），单条样本的最坏情况是固定的。
- 精确地说，“每次 2 条”时损失先在这 2 条的 token 上平均，改成 1 条后变成逐条平均，权重有极小差别。不过上游在 8 卡上的分组方式本来就和我们 4 卡不同，这一点已写进协议补记。

**检索改用 CPU（`FAISS_GPU=0`）不采用**：
- CPU 上的 Flat 索引没有 GPU 加速，每查一次都要扫一遍全部约 64 GB 的向量。
- 每步约有几千次检索，集中在采样前段同时涌来，每次几百毫秒还要互相争内存带宽，会把每步拖慢一倍以上。
- “1.5 次/秒”是整步的平均值，掩盖了前段的高峰。
- 检索在卡 0 上占的约 13.9 GB 是固定开销，不会增长；真正增长的是训练侧。

**仍然 OOM 时**（按顺序）：
1. 确认 `patch` 日志里是 `micro-batch 1` 和出题者显存比例 0.25；
2. `export EXPANDABLE_SEGMENTS=1` 后重跑 `patch` 和这一轮（缓解碎片，先确认能正常启动）；
3. 把 OOM 报错的完整最后 30 行（含 “reserved but unallocated” 那一行）发回家服。

生成题池阶段 OOM 用 `GEN_MEM=0.7`。任何情况下都**不要把显存比例往上调**。看板会在任一张卡显存超过 93% 时标红提醒。
