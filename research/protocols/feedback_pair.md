# 可验证反馈组合首筛冻结协议

## 研究主张

从同一出错状态的交叉反馈里学习用例的交互效应，可以在相同推理额度下提高新题的修复成功率。选择器只在当前验证器能提供真实输入和参考输出的环境下使用。冻结修复模型，用程序执行结果产生学习目标。

## 题目与判分

数据固定为 `deepmind/code_contests` 原始训练集修订 `802411c3010cb00d1b05bad57ca77365a3c699d6` 的 39 个分片。内部开发集与封存集均从这些分片取，标准测试集保留给后续验证。仅用有 Codeforces 竞赛编号、标准输入输出和可复验 Python 3 参考程序的算法题。按规范化题干开头去重，按竞赛编号整体拆分。按固定哈希顺序，每组最多取 1,152 道通过参考执行检查的题。每题只采一个首答。

每题最多 12 条生成测试用于可见反馈，从私有测试保留 8 条评分测试。使用规范化输入与同形单 token 改动排除相近用例。已摘取的公开例、反馈例和评分例之间执行显式检查。单 token 邻居规则覆盖局部近重复。运行参考 Python 3 解验证输入输出。判分采用空白归一后的精确 stdout，输出不唯一的题型从文本筛查和参考执行中排除。候选程序逐例在隔离进程执行，执行到期、异常、无法解析和生成截断按失败记录。原首答是否触发修复仅取决于可见测试。封存分数仅用于目标和评估。

数据准备每组至少 384 个通过参考执行的任务才能启动。固定模型分词后排除超出首答提示上限的题目并记录数量。GPU 首答后，训练和封存各须至少 384 道具备两条有效失败和两条通过反馈的真实失败。训练取前 384 道合格任务，封存评估覆盖固定名单里的全部可见失败。无法组成四格时所有方法采用相同的重新作答回退。冒烟仅取训练集前 32 道，至少一套完整真实四格。冒烟验证数据、四卡与判分链路。

## 方法、对照与预算

固定冻结约 3B 的本地 safetensors 模型。四卡独立生成，BF16，温度 0.7，top-p 0.95，3072 token 请求上限，其中生成最多 640。每组反馈、双失败和重新作答各两次独立采样；同一修复回合只返回两条例子。反馈臂提示长度差上限为 96 token。

四格包括相似度最高的一过一错组合。其余一过一错分别使用预先排序的首个备选用例。两种选择器使用同一 17 维特征、同一标准化、同一岭系数 0.1、同一四格数据。普通选择器回归每格最终通过率。拟方法增加权重 2 的交叉差残差项，交叉差 `D = (Q11 + Q22 - Q12 - Q21) / 2` 同时用于预测值和实际值。推理选预计通过率最高的一对。对照为相似度、双失败、重新作答和普通选择器。每臂共享首答、可见初测和相同的独立判分额度。

报告每题两个修复样本的平均完整通过率，再按题平均。报告可用配对比例、全可见失败分母、实际输入输出 token、执行次数、生成与判分耗时、拟合与选择器耗时。总运行上限 12 小时，冒烟上限 30 分钟。中断单列 `INCOMPLETE`。

## 判定

- `GO` 要求封存可配对题比四个预定对照中实测最强的高至少 5 个百分点，按竞赛簇 bootstrap 的四项 Bonferroni 同时区间下界均大于零，全可见失败分母同向，且平均实耗生成 token 不超过最强或普通选择器各自的 103%。
- `NO-GO` 表示收益或区间条件未到。`INCOMPARABLE` 表示收益达标但实耗 token 超出匹配范围。`DATA-NO-GO` 表示完整执行完数据或首答筛选后样本量未到。
- 首筛 `GO` 后才注册另一模型与独立题库的复验。首筛统计来自本数据候选和一次修复的具体部署设置。

近邻对照见 [ContrastRepair](https://arxiv.org/html/2403.01971)、[CTRL](https://proceedings.mlr.press/v267/xie25a.html) 和 [RLEF](https://proceedings.mlr.press/v267/gehring25a.html)。
